# SIGMA Core 不足点・エンジニアリング観点の改善項目

- **対象リポジトリ:** `nishida0402shun-dev/SIGMA-Core`
- **確認基準日:** 2026-10-23
- **確認方法:** GitHub 上の README、ソース構成、テスト構成、設計・監査文書、Actions の公開情報を静的に確認
- **注意:** ローカル VS Code の未 push 変更、実機での動作、未確認の全呼び出し経路までは確認していない。本書はコードレビュー／追加調査の候補をまとめたもので、未実施の試験を失敗・成功と断定しない。

## 1. エグゼクティブサマリー

SIGMA Core には、SQLite 永続化、原本ファイルの Blob Storage、テキスト／PDF 抽出、MCP stdio エントリーポイント、複数の自動テスト、設計文書が存在する。一方、**「CI が通ること」「機能コードが存在すること」「SIGMA Studio から安全に使えること」「配布環境で動くこと」は別々に検証する必要がある。**

現時点で優先して扱うべき領域は次のとおり。

1. 要件・受け入れ基準と実装／テストのトレーサビリティを確立する。
2. 外部入力、認証主体、Workspace スコープ、操作ごとの認可を実際の起動・呼び出し境界まで検証する。
3. DB とファイルシステム上の Blob の整合性、障害時の回復、バックアップ／復元を検証する。
4. 抽出結果の由来・抽出器・バージョン・品質状態を正しく記録し、未対応形式を誤って「対応済み」と表示しない。
5. MCP を実プロセス／実クライアントで試し、許可・拒否・異常終了を検証する。
6. Studio の既存ストアと Core のデータ契約が異なるため、統合前に読み取り専用 PoC と移行・切り戻し計画を用意する。
7. Electron／対象 OS でのパッケージングと SQLite ドライバの互換性を確認する。

## 2. 優先度の定義

- **P0 — 統合・リリースを止める:** データ損失、権限越境、復旧不能などのリスクを解消するまで、本番統合や破壊的操作を許可しない。
- **P1 — 高:** 安全性・データ品質・主要機能の信頼性に直結。次の統合ゲートまでに検証する。
- **P2 — 中:** 保守性、運用性、性能、診断性を改善する。
- **P3 — 低／将来:** 実際の利用要件と計測結果に基づいて実施する。

優先度はレビュー上の推奨であり、障害が実際に発生したことを意味しない。

## 4. 特に注意すべき設計上の原則

### 4.1 Core を Studio の正本ストアへ即時切り替えない

Studio 側の文書／フォルダ／版／復旧情報／共有データと、Core の SourceObject／Blob／Artifact／SourceLocation は同一の契約ではない。データの完全移行、ID 衝突検査、ロールバック、回帰テストが実証されるまでは、既存ストアを維持する。

### 4.2 Workspace を自動選択しない

Workspace はユーザーが明示的に選択する。暗黙の既定 Workspace や ID の文字列変換だけでアクセス先を決めない。主体、Workspace、操作の認可をサーバー側で検証する。

### 4.3 「保存できる」と「解析できる」を分ける

原本 bytes の保存、形式認識、テキスト抽出、レイアウト解析、OCR、意味検索は異なる能力である。対応表は操作ごとに管理し、未検証を対応済みに見せない。

### 4.4 バックアップと復元可能性を別々に証明する

バックアップファイルが作成できても、参照先 Blob が欠落していたり、別バージョンで復元できなかったりする可能性がある。復元テストとハッシュ／参照整合性の照合を必須にする。

### 4.5 MCP の権限を UI 側だけで守らない

MCP／CLI／Web AI／Studio のすべてが共通サービス層を通るようにする。UI でボタンを隠すだけでは認可にならない。読み取り、登録、変更、削除、復元を個別に認可する。

## 5. 推奨実施順

### Phase A — 現行状態の確定

1. main の最新 SHA、ブランチ、未マージ PR、CI を確認する。
2. 本文書の各指摘を最新コードと照合し、「未確認／再現／解消確認／保留」に更新する。
3. 要件ベースラインと受け入れ基準の根拠を整理する。
4. Studio 統合ギャップ監査の記述が現在も有効か再確認する。

**ゲート:** 最新 SHA と根拠が特定できない所見を、確定した現行不具合として扱わない。

### Phase B — データ安全性と権限

1. DB／Blob の不整合と障害時の回復。
2. 隔離データ復旧の完全性と競合処理。
3. 認証主体の信頼境界、Workspace 越境拒否、操作別認可。
4. マイグレーション、重複登録、未知の書き込み結果への対応。
5. バックアップからの実復元。

**ゲート:** データ損失・権限越境につながる重大な未検証項目が残る間は、本番書き込み統合をしない。

### Phase C — 抽出と MCP

1. 抽出来歴の正確性を確認する。
2. PDF fixture と形式別の対応表を整備する。
3. MCP 実プロセスで許可／拒否／無効引数／異常終了を試す。
4. エラーコード、監査ログ、タイムアウト、再試行の挙動を検証する。

**ゲート:** 抽出の出典を追跡でき、MCP の許可・拒否がテストで再現できる。

### Phase D — 配布と Studio 統合 PoC

1. Electron と対象 OS のパッケージで起動・DB 操作を確認する。
2. 隔離されたテストデータを用い、読み取り専用で Studio から Core を利用する。
3. 件数、ハッシュ、ページ出典、検索結果を期待値と照合する。
4. Studio の既存機能の回帰テストを実行する。
5. 正本切替を提案する場合は、移行・切り戻し計画を別途作り、明示承認を得る。

**ゲート:** 対象ランタイム、統合経路、回帰テスト、ロールバックの証拠が揃うまでは正本ストアを切り替えない。
