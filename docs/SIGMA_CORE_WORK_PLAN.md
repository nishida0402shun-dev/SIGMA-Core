# SIGMA Core 作業計画書

- 文書種別：実装・検証計画
- 対象：SIGMA Core
- 状態：計画書。記載した作業は、個別に実装・テスト・確認するまで完了扱いにしない。

## 1. 目的

SIGMA Core を、SIGMA Studio の資料管理・抽出・検索・部分取得・AI 向け資料提供を支える共通基盤として段階的に整備する。既存コードや会話履歴だけを根拠に実装済みと判断せず、リポジトリとテスト結果を確認する。

## 2. 基本方針

1. 旧式の `SIGMACore` や `knowledgeDB` を無条件に引き継がない。削除・置換の実施状況はコードを検索して確認する。
2. DB は Workspace ごとに分割せず、共通利用を基本とする。Workspace の選択を Core が自動決定しない。
3. Studio の UI と Core のデータ処理を分離し、安定した公開契約で連携する。
4. ファイル形式は段階的に追加し、形式ごとに抽出品質・位置情報・異常系を検証する。
5. 原本、抽出テキスト、位置情報、検索索引、AI 向け出力を区別する。
6. 大きな設計変更は、影響・選択肢・移行方法を提示して合意を得てから行う。
7. 実装済み・テスト済み・CI 確認済み・未確認を明確に区別する。

## 3. Core と Studio の責務

### SIGMA Core
- 資料登録、識別子、メタデータ、原本保管
- ハッシュ等による原本の整合性確認
- ファイル形式判定と抽出器の共通インターフェース
- 抽出テキストと出典位置情報の管理
- 全文検索、絞り込み、部分取得 API
- AI 向け資料パッケージの生成
- データ契約、エラー形式、互換性、テスト

### SIGMA Studio
- 資料一覧、ビューアー、ページ移動、ズーム、選択等の UI
- 形式別の表示・レンダリング
- ビューアー内に表示されている資料内容のキャプチャー
- AI に渡す内容の確認・編集・送信 UI
- Workspace のユーザー選択
- Core API 接続とエラー表示

### 境界要件
- キャプチャー対象は SIGMA Studio 内の資料ビューアーに表示されている内容に限定する。デスクトップ全体や外部アプリをキャプチャーしない。
- Core はビューアー UI やページ送り UI を実装しない。
- Studio は Core の内部 DB を直接操作せず、公開 API／契約を通してアクセスする。
- Studio の既存保存・読み込み機能を、移行計画なしに一括置換しない。

## 5. Phase 1：原本とメタデータの永続化

作業：
- 資料 ID、表示名、形式、サイズ、登録日時、更新日時等のモデルを確定
- 原本保管インターフェースを確定
- ハッシュ値と読み出し時の整合性確認をテスト
- 重複登録、削除、失敗時の復旧方針を定義
- パストラバーサル等を防止
- 原本・派生データ・索引の削除関係を定義

受け入れ条件：
- 登録した原本を再取得できる
- 改変・破損を検知できる
- 失敗時に中途半端な登録状態を残さない
- データ削除は対象と影響を明示し、承認された手順で行う

## 6. Phase 2：抽出器の共通契約

作業：
- 形式判定、抽出要求、抽出結果、警告、エラーの型を定義
- 抽出器の登録・選択方式を確定
- 文字コード、空ファイル、破損ファイル、サイズ上限、タイムアウトを扱う
- 抽出結果に出典位置情報を保持
- 未対応形式と抽出失敗を区別

受け入れ条件：
- 抽出器を共通インターフェース経由で呼び出せる
- 未対応形式・破損ファイルを明確なエラーとして返す
- 個別の抽出エラーで Core 全体が停止しない
- 位置情報がない場合は、そのことを明示できる

## 7. Phase 3：PDF 抽出と部分取得

作業：
- PDF 抽出ライブラリのライセンス、保守状況、Node/Electron との適合性を確認
- ページ番号と抽出テキストを対応付ける
- 取得可能ならブロック／座標情報を保持
- テキスト PDF とスキャン PDF を区別する。OCR は別機能として扱う
- ページ範囲指定 API と範囲外エラーを実装
- 長大 PDF のメモリ使用量・処理時間を測定

受け入れ条件：
- 指定ページだけを取得できる
- ページ番号が元 PDF と一致する
- 座標情報の有無と精度をテストで説明できる
- OCR 未対応時に抽出不能を通常のテキスト PDF と誤認しない

## 8. Phase 4：対応形式を段階追加

候補順：
1. TXT、Markdown、CSV
2. HTML（安全化を含む）
3. DOCX
4. XLSX
5. PPTX
6. 画像と OCR
7. SIGMA 独自形式・その他

形式ごとに、文字化け、順序、表構造、空白・改行、位置情報、異常ファイル、ライセンス、依存サイズを確認する。マクロ、外部参照、埋め込みファイル等の安全性も評価する。

受け入れ条件：
- 「対応済み」は、代表サンプルと異常系テストを通過した形式に限定する
- 各形式の制約を文書化する
- 未対応機能を対応済みのように表示しない

## 9. Phase 5：共通位置情報モデルと範囲取得

作業：
- 共通 `SourceLocation` 契約を確定
- ページ、文字オフセット、段落、シート、セル範囲、スライド、座標等を必要に応じて表現
- 未対応形式でも利用できる最低限の位置情報を定義
- 位置情報を利用した部分取得 API を実装
- 元資料改訂後に古い位置情報を誤用しない仕組みを定義

受け入れ条件：
- 取得結果から元資料の由来箇所を追跡できる
- 範囲外・無効な指定を拒否できる
- 原本バージョンと抽出結果の対応を管理できる

## 10. Phase 6：検索と AI 向け資料パッケージ

作業：
- 全文検索方式と要件を確定
- 資料 ID、形式、日時等の絞り込みを検討
- 必要な箇所だけ返す部分取得 API を用意
- AI 向けパッケージに本文、出典位置、資料 ID、原本バージョンを含める
- サイズ上限、チャンク分割、重複排除、順序保持を定義
- AI の回答に出典を引き継げる構造を設計
- Embedding／Vector DB は必要性・実行環境・メモリ負荷を評価してから採用判断する

受け入れ条件：
- 検索結果に資料 ID と出典位置が含まれる
- AI 向け出力がサイズ上限を守る
- 出典と本文の対応が崩れない
- Vector DB を採用する場合、通常検索との比較とリソース測定がある

## 11. Phase 7：Studio 読み取り連携 PoC

作業：
- Studio adapter と公開 API の対応表を作成
- 資料一覧、メタデータ、抽出テキスト、部分取得を接続
- ローディング、空結果、破損、未対応形式、接続失敗を確認
- Studio が Core の内部 DB を直接操作していないことを確認
- 既存の保存・読み込みフローを回帰テスト
- Electron 上で確認し、ブラウザーだけで完了判定しない

受け入れ条件：
- Studio が公開契約経由で資料情報を取得できる
- エラーがユーザーに分かる形で処理される
- 関連テストで既存機能への回帰がないことを確認
- PoC 成功と全面移行完了を区別する

## 12. セキュリティと堅牢性

- ファイル名や MIME を無条件に信頼しない
- ファイルサイズ、展開後サイズ、処理時間、ページ数等に上限を設ける
- ZIP 系ファイルの展開爆弾や異常入力を考慮する
- HTML はスクリプト実行・外部リソース読み込みのリスクを管理する
- エラー情報やログに資料本文・個人情報を無条件に含めない
- DB／索引の破損検出と復旧方法を検討する
- 外部プロセスや CLI を使う場合、引数、タイムアウト、終了コードを検証する

## 13. テストと CI

### ユニットテスト
- ID・メタデータ検証
- ハッシュと整合性
- 形式判定
- 抽出器の正常系・異常系
- 位置情報と範囲指定
- 検索結果の出典情報
- AI 向けパッケージのサイズと順序

### 統合テスト
- 原本登録 → 抽出 → 保存 → 検索 → 部分取得
- 破損・未対応・巨大ファイル
- 原本更新後に古い抽出結果を使わないこと
- DB／Blob Store 障害・復旧シナリオ
- Studio adapter と Core API の契約テスト

## 14. 優先順位

- **P0：** 現状・未コミット変更・CI の確認、契約と責務境界の確認、旧実装の残存参照調査、テスト基準取得
- **P1：** 原本保存・整合性、抽出器契約、PDF ページ抽出・部分取得、位置情報モデル
- **P2：** TXT／Markdown／CSV、Office 系形式、全文検索、AI 向け資料パッケージ
- **P3：** Studio 読み取り PoC、OCR、Embedding／Vector DB の採用評価、性能最適化

Phase 0 の調査結果に基づいて順番を更新する。

## 15. 完了判定

- **実装済み：** コードが存在し、意図した機能が実装されている
- **テスト済み：** 関連テストを実行し、結果を確認している
- **CI 確認済み：** 対象コミットの CI 結果を確認している
- **統合確認済み：** Studio／Core 間の実際の連携を確認している
- **未確認：** 根拠となるコード・ログ・実行結果を確認できていない

計画書や PR の作成だけでは、実装完了とはみなさない。
