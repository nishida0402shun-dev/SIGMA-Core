# PDF 抽出スパイク計画

- 実施日: 2026-10-19
- 対象: SIGMA Core
- 状態: 依存追加前の調査・検証計画。現時点では依存は未承認。

## 1. 目的

PDF 抽出を安全に導入するため、ライブラリ候補の技術適合性と実務リスクを検証する。計画書の Phase 3 に沿って、依存追加の前に実証的な検証と受け入れ条件を定義する。

## 2. 基本方針

- PDF 抽出は、現在の実装と同様に fail-closed に扱う。
- PDF を抽出できない場合は「検出済みだが未対応」と明示する。
- 抽出の正しさは、ページ単位のテキスト・出典・制約を伴って検証する。
- ライブラリ固有のオブジェクトモデルを canonical data model にしない。
- ライブラリ導入前に、Lockfile と CI の再現性を確認する。

## 3. 候補と評価方針

### 候補 A: pdfjs-dist

- 長所: 直接 API によるページ単位の文字抽出が可能。PDF.js の標準的な挙動と相性が良い。
- 確認事項:
  - Node 22 / Electron との互換性
  - worker と standard font のパッケージ化
  - 大きな PDF のメモリとタイムアウト制御
  - 暗号化 PDF と変な PDF に対する失敗時の安全性
  - 日本語・英語・列構成の読み順テスト
- 判断: まずは最優先候補としてスパイク対象とする。

### 候補 B: unpdf

- 長所: PDF.js ベースの簡便な API で、ページ抽出やテキスト要素取得がしやすい。
- 確認事項:
  - ラッパーのバージョン依存とビルド代替性
  - page fan-out と画像サイズ・時間制約の扱い
  - 何を「supported」とみなすかの明確化
- 判断: 代替候補として比較対象にするが、まずは direct PDF.js を優先する。

## 4. スパイクの実施順序

1. 代表 PDF サンプルの固定
   - 日本語 1ページ
   - 英語 2ページ
   - 複数列レイアウト
   - 空ページ
   - 暗号化 PDF
   - 破損 PDF

2. 依存候補の install と最小 PoC
   - 1 ライブラリだけを追加して基本抽出を検証
   - 依存の再現性とライセンス情報を記録

3. ページ単位の出典テスト
   - 抽出されたテキストが pageNumber と紐づくことを確認
   - 差分や読み順の誤りを検出できるテストを作成

4. 失敗時の安全性
   - malformed / encrypted / huge file で fail-closed になっていることを確認
   - グレースフルな warning を返すことを確認

5. 依存の本格適用判定
   - 検証結果を記録し、依存追加の承認条件を満たした時だけ承認する

## 5. 受け入れ条件

- 指定した pageNumber と抽出テキストが対応する
- 例外 PDF では未対応を明示し、Core 全体が停止しない
- 日本語・英語のページ境界と読み順が検証できる
- 巨大 PDF と不正 PDF で上限と失敗時の挙動を定義できる
- PDF 抽出のライセンスと transitive dependency を確認できる
- package-lock と CI の再現性が整ってから依存を採用する

## 6. 今回の判定

現時点では、依存追加は未承認である。候補は pdfjs-dist を最初のスパイク対象とし、必要に応じて unpdf を比較する。最初のエントリーポイントは「抽出できるか」でなく、「page provenance と fail-close を証明できるか」である。
