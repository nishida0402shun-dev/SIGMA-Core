# SIGMA Core 開発計画・統合前ゲート

**作成日:** 2026-10-17  
**状態:** 開発計画案。正式な要件定義やユーザー承認の代替ではない。  
**対象:** SIGMA Core。SIGMA Studio本体への統合は、最終ゲート通過まで行わない。

## 1. 目的

既存Studio機能を維持しながら、Coreの要件適合性、データ整合性、認可、ファイル抽出、MCP、バックアップ/復元、配布環境を証拠に基づいて検証する。コードやアダプターが存在することだけで、機能完成とは判定しない。

## 3. フェーズ計画

### Phase 0 — 要件ベースラインの再構成・トレーサビリティ

**作業**
1. docs/REQUIREMENTS_BASELINE.md を基準に、現存する決定・設計目標・新規提案を区別して整理する。
2. CORE-Axx / CORE-Bxx / CORE-Cxx を要求文、実装箇所、正系/負系/異常系テスト、CI実行に紐付ける。
3. 承認済み設計と提案段階の文書を区別する。

**完了条件:** 再構成した要件に根拠区分と状態があり、旧AT番号の意味が不明なものは新しい意味を割り当てず、未確認として保持する。

### Phase 1 — データ整合性・CI

**作業**
1. 登録、重複、再試行、同一idempotency keyの不正再利用、DB書き込み失敗をテストする。
2. orphan/missing/corrupt blobの検出と、レポート実行前後でデータが変化しないことを検証する。
3. PR #17をレビューし、採用判断を記録する。自動削除・自動修復は追加しない。
4. Node 22/24で `npm ci`、依存監査、ライセンス確認、テスト、型検査のCI結果を確認する。
5. スキーマ変更時の移行失敗・再実行・復元経路を検証する。

**完了条件:** 重大な整合性不具合がなく、異常系テストとNode 22/24の必須CIが成功する。

### Phase 2 — ファイル認識・抽出・出典追跡

**作業**
1. 形式×操作ごとに、認識、抽出、部分抽出、出典位置、警告、制限、依存関係、ライセンスを一覧化する。
2. PDFはテキストPDF、スキャン、複数ページ、空ページ、破損ファイル等の固定fixtureで精度を検証する。
3. DOCX/XLSX等の候補ライブラリは、バージョン、ライセンス、セキュリティ、代表データでの結果を確認してから採用する。
4. 原本、抽出テキスト、AI整理情報、学習コンテンツを分離し、由来を追跡可能にする。
5. 不確かな範囲を明示し、推測を原本由来の抽出結果として登録しない。

**完了条件:** 対応形式に期待値とテスト証拠があり、未対応形式・制約・出典追跡の限界が明示されている。

### Phase 3 — 認証・認可・Workspace・MCP

**作業**
1. Studioセッションと外部integration identity、subject、Personal/Workspace/shared-library scopeの関係を定義する。
2. 読み取り・登録・変更・削除・復元などの操作ごとに認可をサービス層で強制する。
3. Workspaceは自動選択せず、呼び出し元が明示したIDを検証する。
4. MCP stdioを実プロセスで起動し、許可/拒否、無効な引数、タイムアウト、再試行、異常終了をテストする。
5. 信頼済みidentityをMCPのツール引数から受け取らない。

**完了条件:** 権限マトリクスとテストが一致し、実MCPクライアントによる許可/拒否の動作を確認できる。

### Phase 4 — バックアップ・復元・端末隔離・障害回復

**作業**
1. バックアップ完了と復元可能性の検証を別々に扱う。
2. 全体・カテゴリ・単一レコードの復元で、事前影響確認、認可、復元後検証を確認する。
3. 端末隔離/失効時の許可・拒否操作を要件に沿って検証する。
4. 容量不足、破損バックアップ、中断、部分失敗、再試行、監査記録を試験する。

**完了条件:** 新規ディレクトリ等に復元し、件数・ハッシュ・参照整合性を照合した証拠がある。

### Phase 5 — Electron配布とStudio統合準備

**作業**
1. SQLiteドライバ/native addonのElectron ABI、パッケージング、対象OSとの互換性を確認する。
2. 対象OSでクリーンインストール、起動、登録、検索、再起動、バックアップ/復元を試す。
3. CoreをStudioに接続する場合は、最初に隔離された読み取り専用PoCを行い、既存Studioストアを正本として維持する。
4. 移行する場合は、ID衝突、フォルダ、版、履歴、共有データ、サイドカー、ledger、復旧ファイルの照合と切り戻し手順を別途作成する。

**完了条件:** 配布環境での実行記録、Studio回帰テスト、移行/切り戻しのレビュー証拠がそろう。

## 4. Studio統合前の必須ゲート

- [ ] 再構成した要件ベースラインの根拠区分と承認状態が明確で、適用する要件が実装・テスト・CIに追跡されている。
- [ ] 重大なデータ整合性・認可・セキュリティ問題が残っていない。
- [ ] Node 22/24の必須CIが成功している。
- [ ] ファイル形式ごとの抽出能力・制限・出典追跡が検証済みである。
- [ ] MCP実プロセスの許可/拒否・異常系がテスト済みである。
- [ ] バックアップからの復元と整合性検証が成功している。
- [ ] 対象Electron/OS配布環境でDBドライバが動作している。
- [ ] API、identity、Workspace scope、正本ストア方針が合意されている。
- [ ] 隔離した読み取り専用PoCとStudio回帰テストが成功している。
- [ ] 移行と切り戻し計画がレビューされ、明示承認されている。

このチェックリストの達成だけでストアを自動切替してはならない。書き込み経路の切替やデータ移行には独立した変更計画と明示承認を要する。

## 5. 継続して守る制約

- 旧式SIGMACore / `knowledgeDB` を新Coreの基盤として再利用しない。
- DBはWorkspaceごとに分割せず共通DBを基本とする。Workspaceはユーザーが選択する。
- Coreが同等性・移行・復元を実証する前にStudioの既存ストアを置換しない。
- ベクトルDB/Embeddingや追加ライブラリは、要件・代表データ評価・運用コスト・ライセンスの確認前に採用しない。
- blob整合性レポートは読み取り専用とし、削除・修復は別設計・承認・テストとする。
- 実装済み、テスト済み、CI成功、Electron配布検証済みを別の状態として報告する。
- 重大な設計変更は選択肢・影響・代替案を先に提示し、承認を得る。
