# SIGMA Core向け PC最適化OCR 実装計画書

- 作成日：2026-10-23
- 対象：SIGMA Core
- 対象PC：Windows 11 / AMD Ryzen 5 4500U / AMD Radeon内蔵GPU（表示値496 MB）/ RAM 8GB以下
- 優先事項：認識精度
- 状態：実装進行中。Tesseract CLI の最小実装、ページ単位ルーティング、単体画像 OCR、前処理、合成ベンチマークまで追加済み。進捗・未確認事項・実測値は `docs/OCR_IMPLEMENTATION_STATUS_2026-10-25.md` を参照。対象 Windows 11 実機、代表データでの CER/WER、PaddleOCR 比較は未実施。

## 1. 目的

既存のPDFテキスト抽出、ファイル管理、DB、検索機能を可能な限り再利用し、スキャンPDF・画像にOCRを追加する。低メモリ環境で安全に動作させ、教材・一般文書・表・数式・手書き文字などをカテゴリ別に評価する。

### 目標
1. テキスト埋め込みPDFでは既存のテキスト抽出を優先する。
2. OCRは必要なページだけに実行する。
3. CPU推論を必須経路とし、GPU加速は実機で確認できた場合のみ利用する。
4. OCR結果を元ファイル・ページ・モデル・設定と紐付け、再処理可能にする。
5. 精度・速度・ピークRAM・失敗率を測定し、採用エンジンを決める。
6. OSS・モデル・言語データ・依存ライブラリのライセンスを個別に確認する。

### 非目標
- OCRモデルをゼロから学習すること。
- あらゆる数式・手書き文字・表を完全認識すると保証すること。
- 初期段階で有料APIやクラウド処理を必須にすること。
- 実測前に特定モデルが対象PCで動くと断定すること。

## 2. 前提と実装前調査

PC情報はユーザー申告に基づく。GPUの「496 MB」という表示だけでは、共有GPUメモリ総量や推論ランタイムの対応可否は判断できない。初期設計はCPU推論を基準にする。

実装前に必ず確認する：
- SIGMA Coreのmain/HEAD、ブランチ、未コミット変更、PR、最新CI
- PDF抽出、画像処理、ファイル保存、DB、検索、Studio連携の現状
- 現在の言語・ランタイム・依存関係・テスト構成
- OCR関連コードや既存ライブラリの有無
- 対象PCの実RAM、空きストレージ、ランタイム、実行環境
- 既存ライセンスと配布条件

本書のモジュール名は設計上の仮称。既存機能と重複する場合は新設せず、既存実装を拡張する。

## 3. 推奨方針と候補OSS

### 構成方針
1. 既存PDFテキスト抽出を実行する。
2. ページ単位で抽出量・文字化け・読み順等を検査する。
3. 不十分なページだけ画像化してOCRする。
4. 軽量エンジンを基準実装にする。
5. 品質不足のページは前処理の変更や別エンジンで再処理する。
6. 品質を保証できない場合は「要確認」とし、正確だと断定しない。

| 候補 | 役割 | 方針 |
|---|---|---|
| Tesseract OCR 5系 | 日本語・英語の印刷文字の基準OCR | 最初にCPU実行を検証 |
| PaddleOCR通常パイプライン | 文字検出・認識の比較候補 | 同じデータで評価後に採否決定 |
| PaddleOCR-VL-1.6 | 複雑なレイアウト・表・数式等の解析候補 | 低メモリPCで実測するまで実験枠 |
| 既存PDF抽出機能 | テキスト埋め込みPDF | 既存実装を優先して再利用 |

Tesseractを最終的な最高精度エンジンと決めつけない。カテゴリ別の測定結果で採用を決める。

### 公式資料
- Tesseract: https://github.com/tesseract-ocr/tesseract
- Tesseract documentation: https://tesseract-ocr.github.io/tessdoc/
- PaddleOCR: https://github.com/PaddlePaddle/PaddleOCR
- PaddleOCR-VL-1.6 model card: https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.6
- PaddleOCR-VL usage: https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PaddleOCR-VL.en.md
- PyMuPDF licensing: https://pymupdf.io/licensing

導入時点のリリース・モデルカード・依存関係のライセンスを個別確認する。プロジェクト本体のライセンスだけでなく、モデル重み、言語データ、ランタイム、推移的依存関係も台帳化する。PyMuPDF等を新規導入する場合は、既存ライブラリの再利用を優先し、AGPL等の配布条件を確認してから採用する。

## 4. 論理アーキテクチャ

```text
PDF / 画像
  -> 既存のファイル取込・PDFテキスト抽出
  -> ページ単位の品質チェック
       -> 十分なテキストあり：既存抽出結果を採用
       -> 不十分：画像前処理 -> OCRジョブキュー
                    -> 基準OCR -> 品質評価
                         -> 合格：結果保存
                         -> 要確認：前処理変更/別エンジンで再処理
  -> SIGMA Coreの検索・AI連携
```

### モジュール案（仮称）

| モジュール | 責務 |
|---|---|
| `OcrEngine` | 共通インターフェース・共通結果型 |
| `TesseractEngine` | Tesseract呼び出し、タイムアウト、エラー処理 |
| `PaddleOcrEngine` | 採用したPaddleOCRモデルの呼び出し |
| `DocumentRouter` | ページ状態に基づく処理経路の選択 |
| `ImagePreprocessor` | 回転・傾き・ノイズ・解像度調整 |
| `OcrQualityEvaluator` | 実行時品質チェックと再処理判断 |
| `OcrJobQueue` | 逐次処理、進捗、キャンセル、同時実行数制御 |
| `OcrResultRepository` | 元ファイル・ページ・モデル・結果の関連付け |
| `OcrBenchmark` | 正解データとの比較、性能レポート |
| `OcrLicenseInventory` | OSS・モデル・言語データ・依存関係の一覧 |

既存機能がある場合は重複実装しない。具体的な配置や命名は現行アーキテクチャを調査してから決める。

### 共通結果に必要な情報
- 元ファイルID、ページ番号
- 抽出テキスト、取得できる場合はブロック・座標・構造
- エンジン名、モデルID/バージョン、言語、前処理設定
- 成功・要確認・失敗・キャンセルの状態
- 処理時間、警告、エラーコード
- エンジンが返した信頼度と、独自の品質評価結果

エンジンの信頼度は正解率そのものではないため、独自評価と混同しない。

## 5. 低メモリ環境の制御

必須要件：
- OCRジョブの初期同時実行数は1。
- PDF全ページを一括画像化せず、ページ単位で処理する。
- 処理後に画像・バッファ・一時ファイルを解放する。
- OCRを子プロセス等に分離し、ハング・クラッシュをCore本体から隔離する。
- タイムアウト、キャンセル、異常終了、メモリ不足を明示的な状態として記録する。
- 高精度モデル起動前に実行条件を確認し、条件不適合なら保留または基準エンジンに戻す。
- ファイルサイズ、ページ数、画像ピクセル数、処理時間に上限を設ける。
- シェル文字列連結を避け、安全に引数を渡す。
- 同じ入力・モデル・設定の重複処理を避ける。
- メモリ閾値はOSとStudioを含む実測に基づいて決める。

## 6. 文書カテゴリ別の扱い

| カテゴリ | 評価・処理上の注意 |
|---|---|
| 日本語・英語印刷文書 | 言語設定、文字誤り率 |
| 縦書き | 読み順、句読点、段落順 |
| 表・段組み | セル対応、行列、読み順 |
| 数式 | 演算記号、分数、添字、構造 |
| 手書き文字 | 一般OCRで対応できると仮定せず、別評価 |
| 低画質スキャン | 傾き、ぼけ、ノイズ、薄い文字 |
| 写真 | 回転、遠近、照明むら、背景 |
| 混在言語 | 言語組合せごとの精度と速度 |
| テキスト埋め込みPDF | OCR不要判定が正しいか |

前処理は常に全部適用せず、原画像と補正画像を同一データで比較する。

## 7. DB・結果保存

保存する項目：
- 元ファイルIDとページ番号
- OCR結果テキストと取得可能な構造情報
- エンジン・モデル・バージョン・設定
- 処理状態、時間、警告、エラー
- エンジン信頼度と独自品質評価
- 元ファイルの既存識別子またはハッシュ
- 再利用キー、作成日時、再処理履歴

保存原則：
- 元ファイルは上書きしない。OCR結果は派生データとして扱う。
- 現在採用中の結果と過去の処理履歴を区別する。
- DB保存失敗時の部分データや一時ファイルを適切に処理する。
- マイグレーション、ロールバック、既存データ検証を行う。
- DB構造は現行の共通DB設計を確認してから決める。

## 8. ベンチマーク計画

### 評価データ
初期評価用として100〜200ページ程度を提案する。固定要件ではなく、代表性と作成コストを見て調整する。人が確認した正解テキストを用意し、文書カテゴリを付与する。著作権・個人情報・利用権限に注意し、評価データを無断で外部送信しない。

### 指標
- CER（文字誤り率）：`(置換数 + 削除数 + 挿入数) / 正解文字数`
- WER（単語誤り率）：日本語の分かち書き方式を固定して比較
- レイアウト品質：読み順、段落、表の行列、見出し
- 数式品質：記号、分数、添字、構造
- 速度：初期化時間、ページごとの中央値・95パーセンタイル
- メモリ：起動時・ピークRAM、長時間処理時の増加
- 安定性：失敗率、タイムアウト、クラッシュ、キャンセル成功率
- リソース：CPU使用率、一時領域、モデル容量
- 回帰：既存PDF抽出・検索結果の劣化がないこと

### 比較する構成
A. 既存PDF抽出のみ  
B. Tesseract単独  
C. PaddleOCR通常パイプライン  
D. 前処理あり/なし  
E. 品質判定付きハイブリッド  
F. PaddleOCR-VL-1.6（CPUで実行できる場合のみ）

同じ正解データ・同じ設定で比較し、初回起動とウォーム実行を分ける。不要アプリを閉じた条件と、通常のStudio稼働条件を両方測る。

### 暫定受け入れ基準
以下は計画上の目標であり、公式保証や実測結果ではない。

| 項目 | 暫定基準 |
|---|---|
| 通常の日本語印刷文書 | CER 5%以下を目標にカテゴリ別評価 |
| 低画質文書 | 基準構成に対する改善を確認 |
| 表・段組み | 読み順と構造を別指標で合格判定 |
| 数式 | 記号・添字・分数を専用サンプルで評価 |
| 手書き | 対応範囲と失敗条件を明記 |
| 安定性 | 長時間処理でクラッシュ・データ破損なし |
| メモリ | 実測で定めた上限を守り、超過時は安全に保留/失敗 |
| 再現性 | モデル・設定・入力を記録し再評価可能 |
| 回帰 | 既存テストと関連統合テストが成功 |

通常文書のCER達成だけで、数式・表・手書きの合格を代替しない。最終閾値はベースライン測定後に確定する。

## 9. テスト計画

### 単体テスト
- 結果形式の変換、ページ番号・座標・言語の保持
- エンジン成功、失敗、タイムアウト、キャンセル
- 空白・画像・テキスト埋め込みページの判定
- 品質評価と再処理判断
- 不正なパス・ファイル・入力値
- 重複排除キー、結果保存、保存失敗時の回復
- 一時ファイルの削除と信頼度の扱い

### 統合テスト
- テキスト埋め込みPDFを既存経路で処理する
- スキャンPDFをページ単位でOCRする
- 混在PDFでOCR対象ページだけ処理する
- 結果と元ファイル・ページが正しく関連付く
- 結果が検索対象に含まれる
- 再処理後も元ファイルが変更されない
- OCRプロセス異常終了時もCore/Studioが継続動作する
- キャンセル、再開、重複実行が安全
- DBマイグレーション・ロールバックを検証する
- PDF、ファイル管理、検索、MCP等の関連機能に回帰がない

### 負荷・障害テスト
- 大容量・多ページPDF、巨大画像、破損ファイル
- 小さい文字、傾き、低コントラスト、複雑なレイアウト
- OCRプロセスのハング、RAM逼迫、空きディスク不足
- DB保存失敗、同じ文書の連続投入、キャンセル直後の再投入
- 長時間処理でのメモリ増加・一時ファイル残留

CIの成功と実機性能は分けて報告する。対象PCでの実測を必須にする。

## 10. 実装フェーズ

### Phase 0：現状調査・ベースライン
作業：リポジトリ・CI・PDF抽出・DB・検索・Studio連携・依存関係を調査する。  
完了条件：既存機能、変更対象、ベースラインテスト、ライセンスが整理されている。

### Phase 1：軽量OCRの最小実装
作業：Tesseractと日本語言語データのバージョンを固定し、単一ページOCR、タイムアウト、エラー処理を実装する。  
完了条件：対象Windows 11で手順を再現でき、日本語・英語のサンプルを処理し、失敗してもCore/Studioが停止しない。

### Phase 2：PDFページ処理・前処理
作業：既存PDF抽出の再利用、OCR対象ページ判定、画像前処理、進捗・キャンセルを実装する。  
完了条件：不要なOCRを避け、スキャンPDFをページ単位で安全に処理できる。

### Phase 3：保存・品質判定・検索連携
作業：既存DB設計に沿って結果を保存し、品質状態、再処理、重複排除を実装する。  
完了条件：元ファイルとの対応が追跡でき、検索・AI連携と回帰テストが通る。

### Phase 4：PaddleOCR比較・高精度経路
作業：同一データでTesseractとPaddleOCRを比較し、必要に応じPaddleOCR-VL-1.6をCPUで実験する。  
完了条件：カテゴリ別精度、速度、ピークRAM、ライセンスが記録され、採用理由が説明できる。

### Phase 5：最終ベンチマーク・配布準備
作業：回帰・障害テスト、ライセンス台帳、導入・更新・再処理手順、運用文書を整備する。  
完了条件：対象PCで再現でき、カテゴリ別の制約・失敗条件・未解決事項が明記されている。

## 11. リスクと対策

| リスク | 対策 |
|---|---|
| RAM不足でモデルが起動しない | 軽量経路を基準にし、モデル起動前に条件を確認 |
| GPUが利用できない | CPU推論を必須にし、GPUは実測後に判断 |
| 数式・表の誤認識 | 専用評価と「要確認」状態 |
| 前処理で精度が低下 | 前処理あり/なしを同一データで比較 |
| OCRがアプリを停止させる | 子プロセス、タイムアウト、キュー、キャンセル |
| DBと結果の不整合 | 派生データ管理、トランザクション、回復テスト |
| ライセンス漏れ | モデル・言語データ・依存関係を含む台帳 |
| モデル更新で結果が変わる | バージョン・設定を記録し、更新時に再評価 |

## 12. セキュリティ・運用要件

- ローカル処理を基本とし、文書を外部送信しない。
- クラウド経路を将来追加する場合は、明示的な設定・同意・送信範囲の説明を設ける。
- ファイルサイズ・ページ数・画像ピクセル数・実行時間を制限する。
- OCRプロセスは必要最低限の権限で実行する。
- 一時ファイルを安全に保管し、終了後に削除する。
- ログに文書本文や個人情報を不用意に出力しない。
- モデルの取得元・バージョン・ハッシュを記録する。
- 利用者に進捗、失敗、要確認、使用エンジン、処理時間、再処理方法を提示する。

## 14. 実装開始時の最初のタスク

1. SIGMA CoreのHEAD、ブランチ、作業ツリー、CIを確認する。
2. PDF抽出、ファイル管理、DB、検索、テスト、Studio連携の実装箇所を特定する。
3. OCR関連コード・依存関係があれば再利用候補として評価する。
4. 対象PCの実RAM、空きディスク、ランタイム、インストール状況を確認する。
5. 別ブランチでTesseractの最小プロトタイプを作成する。
6. 代表的な評価データと正解テキストを用意し、ベースラインを測る。
7. 結果に基づいてPaddleOCR系モデルの比較対象と採用条件を決める。
8. 小さな単位で変更し、関連テストを実行してから統合する。

大規模なDB変更、既存ストアの切り替え、破壊的なデータ移行は、本計画書だけを根拠に実行せず、差分・移行・ロールバック・回帰テストを提示して承認を得る。

## 15. 作業報告フォーマット

各フェーズの報告には以下を含める。
- 変更内容：ファイルと設計上の理由
- テスト：実行コマンド、対象、成功・失敗件数
- 実機測定：PC、入力データ、CER/WER、速度、ピークRAM
- ライセンス：OSS・モデル・バージョン・条件
- 未解決事項：未対応文書、失敗条件、性能制約
- 次の作業：根拠と優先順位

テストやベンチマークを実施していない場合は「未実施」と記録し、成功したと表現しない。
