# SIGMA Core 教材データ基盤 作業計画書

**対象リポジトリ:** `nishida0402shun-dev/SIGMA-Core`  
**関連リポジトリ:** [SIGMA Studio](https://github.com/nishida0402shun-dev/SIGMA-Studio-main)  
**文書状態:** 実行計画案。実装完了報告ではない。  
**作成日:** 2026-10-19  
**目的:** SIGMA Studio の汎用教材ビューアが利用する、原本保存・形式別抽出・部分取得・出典追跡の基盤を SIGMA Core に構築する。

> この文書は既存の `docs/DEVELOPMENT_PLAN.md` を置き換えない。Core全体の統合前ゲートに対し、本書は「教材の表示・選択・AI向けエクスポートを支えるデータサービス」に範囲を絞った実行計画である。Studioの画面・レンダリングUIはStudio側の計画で扱う。

## 1. 設計原則

1. **Coreはデータサービスを担い、ビューアUIを持たない。** UI、レンダリングコンポーネント、選択ハンドル、画面キャプチャUIはSIGMA Studio側に置く。
2. **原本を正本として保持する。** 原本バイト列を抽出処理で変更しない。抽出テキスト、OCR結果、AIによる整理情報、学習コンテンツを原本と区別する。
3. **共通DBを維持する。** WorkspaceごとにDBを分割しない。Workspaceのスコープと認可情報はレコードに保持し、Workspaceを自動選択しない。
4. **部分取得と出典追跡を第一級機能にする。** AI向けに抽出したテキストや画像から、原本・バージョン・ページ等の位置へ戻れるようにする。
5. **形式の保存対応と解析対応を区別する。** ファイルを保存できるだけでは、その形式の抽出・検索・範囲選択に対応したと判定しない。
6. **証拠のある状態だけを報告する。** 実装済み、テスト済み、CI成功、Electron/対象OS検証済みを別々に記録する。
7. **Studioの既存ストアを早期に置換しない。** 統合の初期段階は読み取り専用PoCとし、移行・書き込み切替は別の承認ゲートにする。

## 2. 現状の根拠とギャップ

確認対象はGitHubの `main` ブランチにあるソースと設計文書。ローカル未コミット変更や、この計画の作成時点での最新CI実行結果は別途確認が必要。

| 領域 | 確認できた現状 | この計画での扱い |

| DB/サービス層 | `CoreRepository` と `CoreService` があり、原本メタデータやWorkspace、検索等を扱う | Studio向けの安定したサービス契約を整える |

## 3. 対象範囲

### 本計画の対象

- 原本ファイルの登録・取得・重複排除・整合性検証
- MIME/内容シグネチャ/拡張子ヒントを区別した形式検出
- 形式ごとの抽出器とバージョン管理
- ページ・段落・スライド・シート・セル範囲等の位置情報
- 文書全体および選択範囲の部分取得API
- 抽出品質、警告、未対応機能の明示
- Studioと共有するサービス契約、認可、監査、テストfixture
- AI向け素材バンドルを作るための中立的な取得結果

### 本計画では実装しないもの

- ビューア画面、ページ送り、ズーム、選択ハンドル等のUI
- Studioビューアの画面キャプチャ操作UI
- Web AIへの自動送信やWeb AI向けMCP接続
- 特定AIサービスのアップロード自動化
- Coreの検証完了前に行うStudio正本ストアの切替
- 形式ごとの検証前に「すべてのファイルを完全対応」と宣言すること

## 4. フェーズ計画

### Phase 0 — 現行契約・要件・依存関係の確定

**作業**
1. `docs/REQUIREMENTS_BASELINE.md`、`docs/DATA_CONTRACT.md`、`docs/DECISIONS.md`、本書の要求と根拠を照合する。
2. `SourceObject`、`ExtractedArtifact`、`SourceLocation`、`SearchHit` とDBスキーマの実態を照合する。
3. Studio側の `LocalSigmaDocStore` / `SharedWorkspaceDocStore` とCoreアダプターのAPI・ID・版・削除・復元モデルの差分表を作る。
4. 形式別候補ライブラリについて、保守状況、ライセンス、セキュリティ、Node/Electron互換性、メモリ消費を評価する。
5. 各形式の操作能力を「検出」「原本保存」「全文抽出」「部分抽出」「構造保持」「位置追跡」「レンダリング補助」に分けた対応表を作る。

**成果物**
- 形式×機能の対応表
- API/データモデルの差分表
- 依存ライブラリ評価記録
- 要件・テスト・CIのトレーサビリティ表

**完了条件**
- 未決事項と決定済み方針が区別されている。
- 既存DBやStudioストアを破壊的に変更する提案が混入していない。
- 採用ライブラリにライセンス・互換性の未評価項目が明記されている。

### Phase 1 — 登録・原本取得・整合性の強化

**作業**
1. 登録時に原本バイト列、SHA-256、バイト長、検出結果、Workspaceスコープ、由来情報を整合的に扱う。
2. 同一内容の重複登録、同一idempotency keyの再試行、キーの不正再利用を検証する。
3. 原本取得APIに認可を適用し、返却バイト列のハッシュを検証できるようにする。
4. DBトランザクションとファイルシステムの境界で発生する孤立Blob、参照先欠損、破損を読み取り専用レポートで検出する。
5. 削除・隔離・復元状態の原本が検索や取得から漏れないことをテストする。

**受け入れ条件**
- 同じ原本を繰り返し登録しても二重の正本が作られない。
- DB登録失敗時に、正本レコードが半端な状態で残らない。
- Blobの不整合検査は、検査の名目でデータを自動削除・修復しない。
- 権限のない呼び出し元は原本バイト列や抽出内容を取得できない。
- 正常系と異常系のテストがあり、実行結果が記録されている。

### Phase 2 — 形式検出と抽出器の契約

**作業**
1. 拡張子だけで対応形式と断定せず、内容シグネチャ、MIMEヒント、解析結果を分けて記録する。
2. 抽出器の共通契約に、形式、抽出器ID/バージョン、complete/partial/failed、警告、出典位置、処理統計を含める。
3. 抽出に失敗した場合に、空文字列を成功扱いしたり、AIの推測で原文を補完したりしない。
4. サイズ上限、タイムアウト、キャンセル、破損ファイル、暗号化ファイル、パーサー例外を明示的に扱う。
5. 依存ライブラリの入力検証と、ZIPベース形式の展開爆弾・過大展開・パストラバーサル等のリスクを評価する。

**受け入れ条件**
- 検出成功と抽出成功が別々に記録される。
- 未対応形式は理由とともにunsupported/unverifiedとして返る。
- 部分抽出は部分であることと警告を返す。
- 代表fixtureと破損fixtureに期待値が定義される。

### Phase 3 — PDF抽出とページ/領域の出典追跡

**優先度:** 最優先の形式別実装候補。ただしライブラリ評価後に採用を確定する。

**作業**
1. テキストPDFとスキャンPDFを区別し、PDFパーサーとOCRの役割を分離する。
2. ページ単位のテキスト、ページ番号、抽出器バージョン、警告を保持する。
3. ライブラリが信頼できる座標を提供する場合のみ、テキスト範囲とページ上のBoundingBoxを関連付ける。
4. 選択ページ・ページ内矩形・テキストオフセットで部分取得できる契約を定義する。
5. OCRを使う場合は、OCR由来であること、言語、信頼度（取得できる場合）、失敗状態を記録する。
6. ページ回転、CropBox、空ページ、複数カラム、数式、表、埋め込み画像、破損・暗号化PDFのfixtureを整備する。

**受け入れ条件**
- テキストPDFとスキャンPDFを誤って同じ能力として報告しない。
- 指定ページの抽出結果がそのページの原本に追跡できる。
- 座標を取得できない場合は座標を捏造せず、機能制限を返す。
- fixtureごとに期待テキスト、ページ番号、許容差、警告が定義されている。

### Phase 4 — Office・表計算・テキスト・画像の段階的対応

各形式はライブラリ評価とfixture検証を通ったものから実装する。すべてを一括で「対応済み」にしない。

| 形式 | 最低限の抽出目標 | 部分取得の単位 | 注意点 |
|---|---|---|---|
| DOCX | 見出し、段落、表セル、順序 | 見出し/段落/表 | ヘッダー、脚注、画像内文字は別能力として扱う |
| PPTX | スライド、テキスト要素、順序 | スライド/要素 | 図形内テキスト、ノート、埋め込み画像の扱いを明記 |
| XLSX | シート、セル値、式、必要な表示情報 | シート/セル範囲 | 数式と計算結果、表示書式を混同しない |
| CSV | 行列、文字コード、区切り | 行/セル範囲 | 区切り文字、引用符、改行、文字コードを検証 |
| TXT/Markdown/HTML | テキストと構造要素 | 見出し/段落/オフセット | HTMLはスクリプト等を実行せず、抽出用に解析 |
| 画像 | 原本、寸法、形式、任意のOCR | 画像全体/領域 | OCR結果を原本の文字と断定しない |
| SigmaDoc | 既存の正規SigmaDoc構造 | ブロック/問題/図形等 | Studioの正本モデルを勝手に別形式へ変換しない |

**共通受け入れ条件**
- 形式ごとに対応範囲・制限・ライセンス・抽出器バージョンが記録される。
- セルやスライド等の構造が失われる場合、その制約を明示する。
- 部分取得結果から原本オブジェクトと位置情報を追跡できる。
- テストfixtureと回帰テストがある。

### Phase 5 — 共通位置モデルと部分取得サービス

**作業**
1. 現行の `SourceLocation` を調査し、ページを持たない形式をどう表現するかを決める。
2. PDFのページ・矩形、DOCXの段落・表セル、PPTXのスライド・要素、XLSXのシート・セル範囲、テキストのオフセットを、型安全な形式別locationとして表現する案を作る。
3. すべての位置に `objectId`、`sourceVersion`、`contentHash`、`artifactId`、抽出器情報を結び付ける。
4. `getSource`、`getExtractedContent`、`getRange` 等のサービス名・入出力・エラー契約を定義する。名前は既存APIとの衝突を確認してから確定する。
5. 複数の選択範囲を一つの取得要求で扱う場合の順序、重複、無効範囲、版変更時の競合を定義する。
6. ページ座標の正規化単位、原点、回転、スケール、座標の由来を定義する。

**重要な制約**
- 形式ごとの位置情報を、無理にPDFページモデルへ変換しない。
- バージョンが変わった後の古い範囲指定を、無条件に新しい原本へ適用しない。
- 不明な位置や信頼できない座標を推測で補わない。

**受け入れ条件**
- 位置情報から原本・版・抽出結果へ一意に追跡できる。
- 無効な範囲、古い版、アクセス拒否、未対応形式を明示的なエラーとして返す。
- 部分取得のテストで、指定範囲外の内容が混入しないことを検証する。

### Phase 6 — 検索・素材バンドル・Studio向け読み取りAPI

**作業**
1. 検索結果に原本ID、版、位置情報、抜粋、抽出品質・警告を含める。
2. 検索結果を開いて、対応するページ/段落/スライド/セル範囲を取得するAPIを整える。
3. StudioとAIが利用する素材バンドルの中立契約を定義する。候補要素は、manifest、選択範囲、抽出テキスト、必要な画像/ページ資産、原本参照、警告、ハッシュ、生成日時。
4. バンドルの作成は読み取り操作として扱い、原本データを変更しない。
5. バンドルが選択範囲を正確に反映し、必要な出典情報を維持することをテストする。
6. API呼び出しは共通サービス層を経由させ、アダプターからDBテーブルへ直接アクセスしない。

**受け入れ条件**
- 素材バンドルに選択範囲と出典情報が含まれ、利用側が範囲を検証できる。
- 取得不能な素材は黙って省略せず、警告またはエラーとして表現される。
- 生成物から元の原本と抽出器バージョンを追跡できる。
- 認可、監査、削除状態の制約が検索・取得・バンドル作成の全経路で一貫する。

### Phase 7 — Studioとの読み取り専用PoC

**作業**
1. Coreサービスの起動方法、DB/blobパス、ユーザーID、Workspace選択、IPC/プロセス境界を明文化する。
2. Studioが選択したWorkspaceを明示的にCoreへ渡し、自動選択しない。
3. Studioの既存教材ストアは維持したまま、テスト用データをCoreへ登録し、一覧・検索・部分取得を読み取り専用で行う。
4. StudioからCoreへ接続できない場合のタイムアウト、終了、再起動、ユーザー向けエラーを検証する。
5. データID・版・削除状態・認可の対応表を検証する。
6. Electron上で実行し、Node単体テストだけをもって統合成功としない。

**受け入れ条件**
- Studioの既存教材の保存・読み込み・編集・復元に回帰がない。
- Core接続の失敗時に既存ストアのデータが壊れない。
- Workspaceと認可の境界が実際の呼び出しで検証される。
- 読み取り専用PoCのログ・テスト結果・既知の制限が記録される。

## 5. 共通のテスト戦略

### 単体テスト
- 形式検出、抽出器、位置モデル、範囲検証、ハッシュ検証
- 不正な入力、空ファイル、破損ファイル、巨大ファイル、タイムアウト
- 抽出器バージョン変更と同一原本の再抽出

### 統合テスト
- 登録→抽出→検索→部分取得→素材バンドル作成
- DB失敗、Blob書き込み失敗、重複登録、再試行
- 削除・復元・隔離・権限変更後の検索と取得
- 原本バージョン変更時の古い位置指定の拒否または再解決

### セキュリティテスト
- Workspaceを越えた不正アクセス
- 削除済みデータが検索結果やAI素材へ漏れないこと
- 悪意あるZIP/Office入力、パストラバーサル、展開サイズ制限
- HTML/文書内の命令文を実行指示として処理しないこと。抽出コンテンツは非信頼データとして扱う。

### CI/実行環境
- 現行CIのNode.js 22/24で依存監査、ライセンス検査、テスト、型検査を実行
- 変更ごとに実行したコマンドと結果を記録
- Electron native addonや対象OSの互換性は別の実機/配布検証で確認
- 失敗したテストを削除・無効化して成功扱いにしない

## 6. 進行管理と優先順位

| 優先度 | 項目 | 理由 |
|---|---|---|
| P0 | 現行契約・依存・API差分の確定 | 既存ストアや認可を壊すリスクを先に除去 |
| P0 | 原本・Blob・DBの整合性と認可 | データ損失・漏えいを防ぐ基礎 |
| P1 | PDF抽出と出典位置の検証 | 教材ビューアのページ単位利用に直結 |
| P1 | 形式別抽出契約とfixture | 未対応と部分対応を正しく表現する基礎 |
| P1 | 部分取得API・位置モデル | 任意範囲をWeb AIへ渡すための中核 |
| P2 | DOCX/PPTX/XLSX/CSV/画像の段階的対応 | 形式ごとに品質とコストを検証して拡張 |
| P2 | 素材バンドル契約 | StudioからAIへの中立な受け渡しを可能にする |
| P3 | Studio読み取り専用PoC | Core全体の統合ゲートを満たしてから実施 |
| 別承認 | Studio正本ストア切替・移行 | 破壊的影響が大きく、本計画だけでは許可しない |

## 7. 完了判定

この計画の完了は「ファイルを保存できる」ことでは判定しない。少なくとも以下の証拠を揃える。

- [ ] 各対応形式の能力表に、検出・抽出・部分取得・位置追跡・制約が記録されている。
- [ ] 原本と抽出結果が分離され、ハッシュと版を通じて出典追跡できる。
- [ ] 部分取得の範囲が正確で、範囲外の内容が混入しないテストがある。
- [ ] 抽出失敗・部分成功・未対応を正しく返し、成功と偽装しない。
- [ ] 認可と削除状態の制約が検索・取得・素材バンドルに適用される。
- [ ] 依存ライブラリのライセンス・保守・セキュリティ・実行環境が評価されている。
- [ ] Node 22/24の必須CIが対象コミットで成功している。
- [ ] Electron/対象OSの動作は別途検証され、結果が記録されている。
- [ ] Studio読み取り専用PoCで既存機能への回帰がない。
- [ ] 未実装・未検証・既知の制限が明記されている。

## 8. リスクと保留事項

- **抽出品質:** PDF/Officeの見た目を忠実に再現することと、意味構造を正しく抽出することは別問題であり、個別に測定する。
- **メモリ使用量:** 8 GB程度の環境も考慮し、巨大ファイルを無条件に全件メモリ展開しない。ストリーミング、上限、キャンセル、処理時間を評価する。
- **認可:** Coreのsubject identityとStudioのユーザー/Workspaceの橋渡しが確定する前に、本番の書き込み機能を公開しない。
- **形式ライブラリ:** ライブラリ名や採用は、実データの評価とライセンス確認後に決める。
- **移行:** Studioの既存ストアを置き換える移行、双方向同期、書き込み先の切替は別計画・別承認とする。
- **要件トレーサビリティ:** 消失した旧要件定義書の内容を推測して復元したと主張しない。新しい要件は根拠と承認状態を記録する。
